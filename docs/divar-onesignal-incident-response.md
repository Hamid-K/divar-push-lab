# Divar: collecting push evidence from OneSignal

**Hamid Kashfi · 4 October 2026 · LLM-assisted incident-response note**

The [sampled infected `11.14.20-b` APK](evidence.md) contains a notification path that can hand an encoded address to `ReportDeserializer` **when a push is received**. The exact matching code path appears **silent**: it bypasses Divar's ordinary notification construction, and its OneSignal extender does not post an Android notification. This note describes how Divar could use its own OneSignal account to look for qualifying messages and identify devices to examine. No historical matching notification, fetched command, or on-device execution has been recovered in this research. OneSignal records can establish a send or, in some cases, device receipt; they cannot by themselves establish that the inserted worker ran.

## Preserve first

Divar should identify **every OneSignal app and organization used by the Android production build**, record the app IDs, account plan, and connected Firebase project, and preserve the available data before changing keys or configuration. Enumerate all available sends, including dashboard, API, automated/template, and Journey activity where each product view supports it. Preserve the original JSON/CSV exports, UTC export time, filters used, and SHA-256 hashes. Restrict access to recipient IDs and tokens.

| Evidence | Where to collect it | Why it matters and documented limit |
| --- | --- | --- |
| Sent message and settings | Open each sent push's [message report](https://documentation.onesignal.com/docs/en/push-notification-message-reports) in the dashboard; use the [View Messages](https://documentation.onesignal.com/reference/view-messages) and [View Message](https://documentation.onesignal.com/reference/view-message) APIs | Save message ID, `headings`, `contents`, `data`/Additional Data, app/platform, targeting filters or segments, schedule, TTL, status, and counts. API-created messages are documented as retained **30 days**; dashboard-created messages for the app's lifetime. The list API excludes Journey sends. |
| Recipient activity | Each message's **Audience Activity → Export → All activities**, or the [audience-activity export API](https://documentation.onesignal.com/reference/export-csv-of-events) | Save Subscription ID, OneSignal ID, External ID if set, sent/confirmed/clicked/failure times, and error. Activity is documented as retained **30 days** after send. Download generated export files promptly; their links expire after three days. |
| Account and configuration activity | Organization and app **Settings → Audit logs → Export** | Review dashboard notification actions, logins, member/role changes, API-key changes, templates, segments, integrations, and Event Streams; preserve actor, IP, user agent, target ID, and time when present. [Audit-log retention](https://documentation.onesignal.com/docs/en/audit-logs) is **48 hours** on Free/Growth/standard Professional and **90 days** on Enterprise or Professional with the security add-on. The audit API is Enterprise-only. OneSignal does **not** explicitly list API message sends among its logged API-key actions, so an absent audit entry does not clear an API send. |
| Prior Event Stream copies | **Data → Event Streams** configuration and Divar's receiving endpoint, queue, SIEM, or warehouse | If already configured and retained by Divar, [streamed events](https://documentation.onesignal.com/docs/en/event-streams-data) can join message and Subscription IDs and may include custom `message.data`. Streamed `message.contents` is capped at **50 characters**; this is not a complete push-body archive. Enabling a stream now does not recover old events. |
| Current subscription inventory | [Subscription CSV export](https://documentation.onesignal.com/reference/csv-export) | Can connect Subscription IDs to current Android `game_version` (versionCode), OS, model, and Divar's External ID. This is a **current snapshot**, not proof of the app version at an old send. Use historical Divar/device telemetry for version-at-send. |

The short windows matter now: on 4 October 2026, ordinary 30-day API-message and recipient-activity retention may still cover some September sends but generally not the earlier February–August period. Divar should check its own past exports, Event Stream sink, backups, and push-service request logs, and promptly ask OneSignal what additional server-side preservation or recovery is possible. Do not assume such data exists or is recoverable.

For a bulk pull, use an authorized **App API key** to call `GET /notifications?app_id=...&limit=50&time_offset=...`, follow each returned `next_time_offset`, and save every response page. The API can distinguish dashboard (`kind=0`), API (`kind=1`), and automated (`kind=3`) messages; also inspect Journeys in the dashboard because the list API excludes them. Retrieve each candidate with `GET /notifications/{message_id}?app_id=...`, then export its Audience Activity. Keep the credential out of exports and command history. The [pagination rules and kind values](https://documentation.onesignal.com/reference/view-messages) are documented by OneSignal.

## Hunt for the inserted route

Search from **before the earliest observed positive APK, `11.14.10` (archive date 24 February 2026), through the present**. The archive date is not a verified rollout date. Continue after the class-negative `11.15.0-w` (archive date 22 September): phones can retain older affected builds. The observed chain also disappears in sampled `11.14.15-b` and returns in `11.14.16-b`; `11.14.19-b` retains the worker but its inspected sender lacks this relay. Treat each build and distribution variant separately. The companion DFIR archive's `release_code_audit.md` records the sampled boundaries; the [lab evidence](evidence.md) records the `11.14.20-b` branch.

For each saved OneSignal message, inspect **all localized title/body variants** and Additional Data. The high-confidence candidate is the *combination* below:

1. A nonempty notification title exactly equals Additional Data `push_id`. The sampled OneSignal SDK maps the wire `custom.a` object to the provider data inspected by the Divar handler.
2. The notification body is a JSON **string** with nonempty `callback_url`, `campaign`, and `action` fields.
3. `action` names `ir.divar.chat.notification.provider.ChatPushNotificationOpenHandler`, the receiver observed starting the worker.
4. Offline Base64-decoding of `campaign`, then XOR of each decoded byte with `0x68`, yields the worker's fetch URL. Record the original encoded value and decoded bytes/URL; do not treat `callback_url` as that fetch destination. In this branch `callback_url` is only a nonempty gate.

These field names also occur in clean code; **single-key searches will produce false positives**. Conversely, a changed receiver name, malformed saved representation, or a different delivery route could evade this exact match. Preserve near misses for manual review. A saved OneSignal `data` object is not guaranteed to be a byte-for-byte copy of the FCM wire payload.

## Build the incident chain

For every candidate, join the OneSignal **app ID + message ID + UTC send time** to its targeting expression, exported Subscription IDs, OneSignal/External IDs, and Divar account/device records. Retain the original send request or job from Divar's push backend if available; it may show who submitted the send, exact targeting, and a fuller request body than the current OneSignal view. Check whether the target device had an affected APK installed **at that time**. A dynamic segment or today's Subscription CSV may no longer represent the earlier audience or app version.

Then correlate the decoded `campaign` URL with preserved device/mobile-network DNS and HTTP telemetry and the URL's server/CDN logs where available. Divar's own egress logs would cover that fetch only if the phone used Divar-managed network infrastructure. The strongest evidence of activation would be a matching push receipt followed by a request from that device to the decoded URL and a recovered response or on-device artifact. Preserve downloaded JSON and binary bytes separately with hashes. A OneSignal **Delivered** count means FCM accepted a send; [Confirmed Receipt](https://documentation.onesignal.com/docs/en/confirmed-delivery) means the device SDK sent its confirmation when that paid feature was available. Neither proves that `ReportDeserializer` fetched or executed anything; missing confirmation, a missing click, or an empty Android notification history does not rule it out. In the sampled matching path, the SDK writes `opened=1` to its **local** notification database without a user tap; do not treat that field as evidence of human engagement or assume it matches a cloud dashboard click count.

Keep two outputs distinct. **Potential public IoCs** are a *recovered* decoded fetch URL/domain, the corresponding response or payload hashes, and infrastructure observed serving them after validation. **Case-correlation identifiers** are OneSignal message/app IDs, Subscription/External IDs, target expressions, times, and any supported sender-account/key/IP linkage; these identify possible recipients and operators but should remain in controlled evidence. No fixed attacker domain, IP, or payload hash is known from the APK alone.

## Search outside OneSignal too

The sampled Divar Firebase service has a **direct FCM path** for `source=divar` or `source=default` that reaches the same notification provider. The APK also contains `https://push.divar.ir/_nrto_/` in OneSignal REST-client code, suggesting a Divar-specific SDK transport modification whose full runtime role has not been established. Preserve Divar's push API/queue logs, Firebase sending records where available, `push.divar.ir` reverse-proxy/application logs, credential and change records, and recipient-device evidence. A negative OneSignal search cannot exclude a direct FCM send. Inspect the Divar-hosted SDK/backend endpoint as a separate lead; its presence alone does not establish a push-sending route or make `push.divar.ir` an attacker-controlled `campaign` URL.

**Evidence status:** This is a collection and correlation plan derived from the sampled `11.14.20-b` code path and [OneSignal's product documentation](https://documentation.onesignal.com/docs/en/push-notification-message-reports). Actual Divar account configuration, retention, message history, sender logs, and affected devices have not been inspected here.
